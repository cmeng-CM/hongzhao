# Upgrading hongzhao

**English** | [简体中文](../UPGRADE.md)

Two audiences, one file — same split as [INSTALL.md](INSTALL.md). Humans: three
commands in [Manual upgrade](#manual-upgrade). AI agents: your protocol is
[Agent upgrade protocol](#agent-upgrade-protocol) — follow it when a user asks
you to upgrade hongzhao.

## What an upgrade touches (and never touches)

`pip install -U hongzhao` replaces the engine only. Everything else happens
when you run the upgrade sequence, under these contracts:

| Artifact | Owner | On upgrade | Contract |
| --- | --- | --- | --- |
| engine (pip package) | hongzhao | replaced by pip | — |
| kit `skills/`, `templates/` | package-synced | three-state sync (`skills-install`): identical→overwrite; you edited it→yours stays, new version lands as `.new`; removed from package→kept | your edits always win a `.new` review, never silent overwrite |
| `compiled/`, `render/` | engine | fully regenerated by `compile` | derived data, never migrated; delete+recompile is equivalent |
| client managed block | engine (`bridge-install`) | refreshed from the new bootstrap | content outside `hongzhao:start/end` stays byte-identical |
| `raw/`, `config.yaml`, `registry/`, `projects/` | **you** | **never written** | sources are read-only to the engine; format changes only via an explicit future `migrate` command, never silently |

Version-skew visibility: `doctor` warns `SKILL_STALE` (kit skills synced by an
older engine) and `BOOTSTRAP_STALE` (bootstrap rendered by an older engine)
whenever the kit lags behind the installed package. Both clear when you run
the upgrade sequence.

With `git.auto_commit` enabled (the default for standalone git repos), step 3
of the sequence (`compile`) auto-commits the kit with the stable message
format (`hongzhao compile v<version> ...`); any git failure degrades to a
warning and never blocks the upgrade.

## Upgrade with your AI agent (one line)

Tell your coding agent:

```text
Read https://github.com/cmeng-CM/hongzhao/blob/main/docs/en/UPGRADE.md and upgrade hongzhao for me. My kit is at ~/hongzhao.
```

## Manual upgrade

```bash
cd ~/hongzhao && git add -A && git commit -m "pre-upgrade"  # plain files: git is the safety net
pipx upgrade hongzhao        # or: python3 -m pip install -U hongzhao
hongzhao --root ~/hongzhao upgrade
# expect: upgrade [1/5] ... upgrade: ok (engine <version>)
```

Starting with 0.4.0, `skills-install` prints an `SKILL_UNLISTED` warning
when the package ships a skill your kit's `config.yaml` `skills:` list
doesn't mention yet (e.g. the new `memory-collect`): add a line with the
same name under `skills:` and re-run `hongzhao upgrade` to link it. The
engine never edits your config for you.

`hongzhao upgrade` runs exactly: `validate → skills-install all → compile →
bridge-install all → doctor`, stopping at the first non-zero step. If you
prefer, run those five commands yourself in that order — the command adds
nothing else.

### Troubleshooting

| Symptom | Fix |
| --- | --- |
| stopped at step 2 with `SKILL_MODIFIED ... kept yours; candidate written to ...new` | You customized a kit skill. Diff `SKILL.md` vs `SKILL.md.new`, merge manually, delete the `.new`, re-run `hongzhao upgrade` |
| `warning [SKILL_UNLISTED] memory-collect ...` in the output | A newly packaged skill isn't listed in your kit config: add it under `skills:` in `config.yaml` (e.g. `- memory-collect`), then re-run `hongzhao upgrade` |
| stopped at step 1 (`validate`) | The kit has a source-data problem that predates the upgrade; fix per the validate message first |
| `doctor` warns `SKILL_STALE` / `BOOTSTRAP_STALE` right after `pip install -U` | Expected: the kit lags the new engine. Run `hongzhao upgrade` |
| git diff shows large changes in `compiled/` but `last-compile-diff.md` counts are 0 | Expected: engine releases may reword skeleton text; your records' effectiveness is unchanged |
| need to roll back | `git -C ~/hongzhao checkout .` + `pip install hongzhao==<old>` + `hongzhao --root ~/hongzhao compile` — sources, engine, and derived data roll back independently |

## Agent upgrade protocol

You are an AI coding agent asked by a user to upgrade hongzhao. Execute this
protocol exactly.

1. **Inspect first.** Report `hongzhao --version`, `hongzhao --root <PATH> doctor`
   output, and whether the kit is a git repo with a clean tree — before
   changing anything.
2. **Back up.** If the kit is a git repo, commit everything first
   (`git add -A && git commit -m "pre-upgrade"`). If it is not, say so and
   suggest `git init` (one-time, strongly recommended: memory is plain files,
   git is the backup and the rollback).
3. **Upgrade the package** (`pipx upgrade hongzhao` / `pip install -U hongzhao`),
   then confirm `hongzhao --version` moved.
4. **Run the sequence**: `hongzhao --root <PATH> upgrade`. Do not improvise
   alternative steps; never hand-edit anything under `compiled/`, `render/`,
   or the client managed block.
5. **On failure: stop.** Show the exact output, apply the fix from the
   troubleshooting table (e.g. a `.new` skill conflict needs a human merge
   decision — present the diff, do not resolve it yourself), then re-run
   `hongzhao upgrade`.
6. **Report a short pass/fail table**: package version old→new, the five
   steps' exit codes, and the final `doctor` line. Mention `SKILL_STALE` /
   `BOOTSTRAP_STALE` if they appeared mid-sequence and confirm they are gone.

## Compatibility policy

- **Sources are never auto-rewritten.** `raw/`, `config.yaml`, `registry/`,
  `projects/` keep working as-is across upgrades; a future format change will
  ship an explicit `hongzhao migrate --dry-run` (never silent).
- **New validation rules land as warnings first**, become errors in a later
  release — an upgrade never turns a previously green kit red.
- **New config keys get defaults; renamed keys keep an alias for two minor
  releases.** Unknown extra keys are tolerated (forward compatibility).
- **Downgrade is detected, not silently misread.** If derived outputs were
  produced by a newer engine, `doctor` says so (`BOOTSTRAP_STALE`); re-run
  `compile` with the older engine to realign.
- **Pre-1.0 (0.x)**: minor releases may change kit-visible formats but honor
  every rule above. **From 1.0**: semver applies — major = explicit migration
  required, minor = additive only, patch = no kit-visible change.
